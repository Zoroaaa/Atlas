# Atlas 四类搜索重构设计

> 目标：提升动漫 / 影视 / 漫画 / 小说四类搜索的**准确性、成功率、完整性、可用性**。
> 本文是重构方案，不继承任何既有方案的分期与结论。旧文档 `search-four-category-plan-2026-11-20.md` 降级为核对证据存档（事实与实测数据仍有效，结论以本文为准）。
> 基线：`main` @ `5cd4694`；实测数据采集于 2026-11-20。

---

## 0. 先把"好"定义清楚

四个目标如果不落成指标，改完只能凭感觉。这里定义 6 个指标，其中 1 个是总开关。

### 0.1 核心概念：actionable（可操作结果）

**一个结果只有在用户能对它做点什么时才算结果。** 现在四类都缺这个判定：

- 动漫：Mikan 第 11–30 条 `magnet` 为空，前端渲染成 `href=""` 的链接 + 复制空串；
- 漫画：15/20 的热门作品没有中文译本，卡片上看不出来；
- 小说：详情页解析失败时条目照常展示，但没有下载直链；
- 影视：TMDB 挂了也照常返回空列表，页面显示"没有结果"。

所以先把 `actionable: boolean + reason` 写进内部结果契约。**这一个字段同时驱动三个目标**：可用性（前端不再给死链接）、成功率（"有结果但点不动"不再算成功）、完整性（能统计每类真正可用的结果数）。

| 类别 | actionable 的判定 |
|---|---|
| 动漫 | 资源有磁力且已归属某作品；或作品本身可跳转 Bangumi |
| 影视 | 资源有磁力（网盘需有 `driveUrl`） |
| 漫画 | 至少一种可读语言章节，或存在官方/生肉外链 |
| 小说 | 有 TXT 直链 |

### 0.2 六个指标

| # | 指标 | 定义 | 用途 |
|---|---|---|---|
| M1 | `actionable_rate` | 可操作结果 / 全部结果 | 可用性主指标，也反映准确性 |
| M2 | `success_rate` | 至少 1 条 actionable 的搜索 / 总搜索 | **成功率主指标**，取代"有没有返回 200" |
| M3 | `misattribution_rate` | 人工标注中归属错误的资源比例 | 准确性主指标 |
| M4 | `ungrouped_ratio` | 未归属资源 / 全部资源 | 准确性代理指标（漏配） |
| M5 | `source_coverage` | 实际返回的源数 / 配置的源数 | 完整性 |
| M6 | `p95_latency` / `deadline_hit_rate` | 搜索耗时 p95；撞到时间预算的比例 | 成功率的隐性杀手 |

**基线不靠猜。** 这 6 个指标里 M1/M2/M5/M6 可由 PR-1 的日志直接产出；M3 需要标注，用 M4 和"跨类型误配率"做代理先跑起来。

目标值先定相对值（绝对值等基线出来再定）：`M2 +20pp`、`M3 -70%`、`M4 -30%`、`M5 ≥ 90%`、`M6 p95 < 8s`。

## 1. 为什么现在四个维度都差

不是源不够多，是**四类共用一个错误的前提：资源标题是一段字符串，作品是另一段字符串，两者靠子串包含判断关系。**

```
资源只有标题字符串 ──┐
                     ├─→ 子串匹配 ─┬─→ 错配（Her 抓走 The Mother）──→ 准确性 ↓
作品有多语种名 ──────┘             ├─→ 漏配（罗马音/两字标题）──────→ 完整性 ↓
                                   └─→ 无置信度 → 无法判断该不该归 ─→ 可用性 ↓

失败与空结果同形 ─→ 静默空 ─────────────────────────────→ 成功率 ↓（且不可观测）
无稳定 ID ───────→ 同种子多源不合一 ───────────────────→ 完整性 ↓（重复计数）
只写首条 ────────→ 本地无资产 ─→ 每次全靠现抓 ─────────→ 成功率/时延 ↓
无时间预算 ──────→ 尾部 60s+ ─────────────────────────→ 成功率 ↓（用户已离开）
无 actionable 判定 → 有结果但点不动，指标上还显示成功 ──→ 可用性 ↓ 且看不见
```

五个根因里，只有第一个是"匹配算法"问题，另外四个是**编排与契约**问题。这也是为什么单纯改 `title-grouping.ts` 拿不到全部收益。

## 2. 目标架构

### 2.1 分层

| 层 | 职责 | 关键约束 |
|---|---|---|
| **L0 文本层** | 归一化、切段、发布名结构化解析、候选打分 | 纯函数，零 IO，可 100% 单测 |
| **L1 身份层** | `canonical_work` 统一 ID + 全语种别名 + 身份属性（年份/类型/集数） | 只用 ID 关联，不用标题 |
| **L2 解析层** | 每类把自己的元数据与资源转成统一内部模型 | 网络只在这一层 |
| **L3 结算层** | 召回 → 打分 → 硬约束 → 边际接受 → 去重 → 排序 | 纯计算，输入是 L2 的产物 |
| **L4 存储层** | 作品、资源边、置信度、来源 | 只存元数据与稳定直链 |
| **L5 观测层** | 决策日志、影子回放、标注闭环 | 采样，不阻塞请求 |

**关键点：L2 与 L3 必须解耦。** 现在"抓取 + 判定 + 渲染"合成一个结果直接进 Cache API，导致两个后果：改判定必须等缓存过期（或加版本号硬刷），且无法用真实数据离线对比两套算法。拆开之后：

- 抓取缓存 key = `(category, source, keyword)`，只存原始条目；
- 每次请求重新结算（纯字符串运算，亚毫秒级）；
- 改算法立即对已缓存数据生效；
- 可以把同一份原始数据回放给新旧两套 matcher 做影子对比。

这一条是后续所有准确性改进的前提，也是本文与旧方案最大的结构差异。

### 2.2 两条流水线

四类不是同一种问题，硬套一个归组引擎是错的：

| 流水线 | 类别 | 形态 | 核心问题 |
|---|---|---|---|
| **资源型** | 动漫、影视 | 元数据作品 ← 大量外部资源（磁力） | 实体链接：把资源挂到作品上 |
| **目录型** | 小说、漫画 | 作品本身就是内容入口，没有资源层 | 目录覆盖 + 可读性 |

- 资源型：收益来自"归属正确 + 去重 + 排序 + 可操作"。
- 目录型：收益来自"提前入库 + 本地检索 + 可读性元数据"。小说尤其明显——TXT 是静态资源，最适合目录化。

两条流水线**共享 L0 与 L1**（文本归一化、别名、身份属性），但**不共享结算逻辑**。旧方案试图让四类共用一套 grouping，导致小说/漫画这两个根本没有资源归组需求的类别被强行套上不相关的抽象。

### 2.3 内部统一模型（线上契约不变）

```ts
interface ResolvedWork {
  canonicalId: string;            // bangumi:400602 / tmdb:movie:438631 / mangadex:uuid / novel:zxcs:12345
  category: 'anime' | 'movie' | 'manga' | 'novel';
  displayTitle: string;           // 按用户语言择优（含简繁转换）
  titles: { lang: string; text: string; source: string }[];
  year?: string;
  mediaType?: 'movie' | 'tv';
  totalEpisodes?: number;
  cover?: string;
  meta: Record<string, unknown>;  // 类别特有字段，前端契约不变
}

interface ResolvedResource {
  infoHash?: string;              // 有磁力就有，作为去重主键
  rawTitle: string;
  parsed: ParsedRelease;          // 见 3.1
  workId?: string;                // 归属结果，undefined = ungrouped
  attribution: { score: number; margin: number; reason: string };
  offers: Array<{ source: string; magnet?: string; url?: string; seeders?: number }>;
  actionable: boolean;
}
```

四类对外响应结构**保持现状**（`bgm` / `results` / `manga` / `novels` + `grouped`），中间加一层 adapter。前端零改动即可上线，前端改造放到后续独立迭代——**重构判定层不需要同时重构 UI**。

## 3. 核心算法：从字符串包含到实体链接

### 3.1 资源侧结构化（L0）

`parseReleaseTitle(raw)` 输出：

```ts
interface ParsedRelease {
  segments: string[];   // 按 / ｜ - ： 切段后的归一化片段（保留边界，这是现在丢掉的信息）
  year?: number;
  season?: number;
  episode?: number;
  episodeRange?: [number, number];  // 合集 01-12
  isBatch: boolean;
  resolution?: '2160p' | '1080p' | '720p' | '480p';
  mediaSource?: 'BluRay' | 'WEB-DL' | 'WEBRip' | 'HDTV' | 'DVD';
  codec?: string;
  group?: string;
  subtitle?: string[];
}
```

**必须先切段再归一化。** 现在 `normalizeTitle` 把 `/` 压成空格，`[Group] 银魂 / Gintama - 300` 变成 `银魂 gintama`，分段信息永久丢失——这是"两字标题匹配不上"和"续作吞并"共同的技术前提。

实测确认两件事：年份（`dune 1984 bluray grp`）与 `SxxExx`（`stranger things s04e09 web grp`）在归一化后**仍然保留**，而 `- 05` 已被删除。所以年份可以直接用，集数必须靠独立解析器，不能从归一化结果反推。

### 3.2 打分表

对每个 (资源, 作品) 算分。作品侧候选标题来自 `canonical_work` 的全部别名（v0 同请求返回 / TMDB alternative_titles / 别名表）。

| 特征 | 分值 | 说明 |
|---|---|---|
| 某段与候选标题完全相等 | 100 | 最强正证据 |
| 某段以候选标题开头且后接分隔符/集数/年份 | 85 | 「鬼灭之刃 游郭篇」段 vs 「鬼灭之刃」 |
| 拉丁：候选标题作为**完整单词序列**出现（词边界） | 70 | `Frieren` in `Frieren Beyond Journey's End` |
| CJK：候选标题作为连续子串出现且长度 ≥4 | 55 | 中文无词边界，只能靠长度换精度 |
| 年份一致 | +15 | |
| 年份差 1 | +8 | 首映/发行年常有差 |
| 集数在作品集数范围内 | +5 | |
| 季号一致 | +10 | |
| 该字幕组历史上归属过同一作品 | +5 | 弱信号，用于稳定抖动 |

**负特征（直接否决，不参与打分）**：

| 约束 | 条件 | 为什么 |
|---|---|---|
| 媒体类型互斥 | 资源含 `SxxExx`/`Season N`，作品是 `movie` → 否决 | 现在会把剧集包归给同名电影 |
| 年份窗口 | 电影 `|Δyear| ≥ 2` → 否决 | 同名不同年的唯一硬解 |
| 集数上限 | 资源集数 > 作品总集数 + 2 → 否决 | 防"300 集资源挂到 12 集番" |
| 季号冲突 | 资源 S03，作品 S01 → 否决 | 需季号可得；不可得则降级为扣分 |

约束的可得性要分清：**年份**（免费，从标题解析）、**动漫总集数**（Bangumi `eps`，免费）可立即用；**影视总集数**需要额外 detail 调用，v1 不做，用"季号 + 年份"替代。

### 3.3 边际接受（本文最关键的一条规则）

```
top1 ≥ 60 且 (top1 - top2) ≥ 12  → 归属 top1
否则 → ungrouped
```

现在的实现是"命中即归属、先到先得"，所以 `鬼灭之刃` 会抢走 `游郭篇` 的资源。改成边际接受后：

- 游郭篇资源：top1=100（游郭篇段完全相等），top2=85（基础名前缀）→ 差 15 → 归游郭篇 ✅
- 基础资源：top1=100（基础名段相等），top2=0（游郭篇不是它的前缀）→ 归基础 ✅
- `The Mother` 对 `Her`：词边界不成立 → 0 分 → ungrouped ✅

**规则背后的取舍：宁可漏，不可错。** 错配的代价是用户下载错内容，漏配的代价是多看一屏"其他资源"。前者摧毁信任，后者只是不便。所以阈值宁高不低，未达线的进 `ungrouped` 但**照样展示**（这是完整性兜底）。

### 3.4 短标题规则

`银魂`、`It`、`Up`、`Us` 这类 2 字符标题不能靠文本，只能靠上下文：

- CJK 两字：只接受"段完全相等"；
- 拉丁两字：只接受"整词出现 **且** 年份一致"。

`It (2017)` 因此能命中，而 `It Follows (2014)` 会被年份否决。**短标题必须靠年份，长标题靠文本**——这条规则取代了现在的一刀切 3 字符下限。

### 3.5 去重

去重键从"magnet 字符串"改为 `infoHash`（hex/base32 统一）：

- 同一种子来自 Mikan / AnimeTosho / DMHY → 合并成一条资源、多个 `offers`；
- 展示时保留各源标签，做种数取最大值；
- 落库时 `info_hash` 建索引，跨搜索也能识别同一种子。

现在动漫侧 `resourceId = r.magnet`，而各源 `dn` 与 tracker 不同，**同一种子永远合并不了**（实测确认）。这是"完整性"里最容易修的一块。

## 4. 分类设计

### 4.1 动漫（资源型）

| 项 | 设计 | 为什么 |
|---|---|---|
| 元数据 | Bangumi **v0** `POST /v0/search/subjects`（`limit=10&offset=N`） | 旧接口的 `infobox` 为空，拿不到别名；v0 同请求返回 `别名`，首次搜索即生效，不依赖"先灌库" |
| 别名 | v0 响应内的 `别名` 直接进候选；库内别名（`listAliasRowsByCanonical`）做跨源补充 | 只读库会踩冷启动：别名在搜索后才 `waitUntil` 灌入，而首次结果已被缓存 10 分钟固定 |
| ID 关联 | 优先，作为下一阶段：建立 Mikan 番剧 ID ↔ Bangumi ID 映射（Mikan `<link>` 指向番剧页，URL 是否含稳定数字 ID 需实测） | 标题匹配的天花板只能靠 ID 突破；未验证前不作为前置条件 |
| 集数 | `eps` 进硬约束；资源按 `season/episode` 三层展示，合集单独一组 | 番剧天然按集组织，平铺 100+ 条等于让用户自己找 |
| 排序 | 有做种数才按做种数；无做种数的按「分辨率 → 字幕语言 → 组可信度 → 时效」打分 | 现在四源里只有 AnimeTosho 有做种数，`sortBy=seeders` 实际是"按源排序" |
| 空磁力 | `magnet` 为空的行改为"去详情页"入口，不给死链接 | 现状 `href=""`，点击刷新页面 |

### 4.2 影视（资源型）

| 项 | 设计 | 为什么 |
|---|---|---|
| 元数据 | TMDB 中英两路 **合并**去重，不再丢弃英文独有结果 | 现在只用中文结果，英文结果仅用于取搜索词 |
| 失败可见 | 去掉 `searchTMDB(...).catch(() => [])` | 该 catch 让 `tmdbError` 恒为 null（死代码），TMDB 全挂时页面显示"没有结果" |
| 资源分类 | TPB `cat=200`，并用响应 `category` 字段二次校验 | 实测 `q=her&cat=0`：100 条里 85 条属 5xx 成人分类，Top20 有 16 条非视频；`cat=200` 干净 |
| 并发 | 真正的并发上限 3（`mapWithConcurrency` + 内部 try/catch 保留部分成功） | 现在 `.map(async)` 一创建就发请求，6 个关键词同时打出去 |
| 关键词 | 按作品轮转（每个作品先主标题、再年份变体、最后别名），不再简单 `slice(0,6)` | 同一作品的两个变体会挤掉其他作品的关键词 |
| 华语片 | 若关键词全为非拉丁，**同步**取 top-1 的 `alternative_titles` 补英文名 | 别名是搜索后灌的，首次搜中文片名 TPB 必然 0 条，且被缓存 10 分钟 |
| 季集 | EZTV 用 `page` 翻页（`torrents_count` 给真实总数），用返回里的 `season`/`episode` **本地分组** | 实测 `season`/`episode` 参数被忽略；《权游》有 146 条而当前只取 30 条 |
| 类型约束 | 电影拒绝 `SxxExx` 资源；剧集不要求年份 | 电影收到剧集包是当前错配的一大来源 |

### 4.3 漫画（目录型）

| 项 | 设计 | 为什么 |
|---|---|---|
| 标题 | `title.zh → zh-hk(转简) → title.en → altTitles 中的 zh/zh-hk/en → ja-ro` | 实测 Top20：`title` 含中文 0/20，只有罗马音 19/20 |
| 简繁 | 用 `opencc-js`（已是依赖）把 `zh-hk` 转简 | 中文名大多落在 `zh-hk`，简体用户看到繁体同样别扭 |
| 可读性 | `availableTranslatedLanguages` 无 zh/zh-hk 时显式标注"暂无中文译本"；`links.raw`/`engtl` 作为官方入口 | 15/20 无中文译本，不提示等于让用户白点 |
| 更新 | 只展示 `updatedAt`，或批量 `ids[]=` 取话数 | `latestUploadedChapter` 是 UUID 不是话数，逐条查会变成新的 N+1 |
| 降级 | MangaDex 失败 → MangaUpdates → Kitsu | 现在只有两级，MangaUpdates 也挂时整类归零 |
| 匹配 | MangaUpdates 补全继续用"归一化全等"，但候选集扩到 `altTitles` | 源码注释记录过 One Piece 串到衍生作的教训，不能放开模糊包含 |

### 4.4 小说（目录型）

| 项 | 设计 | 为什么 |
|---|---|---|
| 目录优先 | 站点的分类/排行/最新页增量入 D1，搜索先查本地，未命中再现抓 | TXT 是静态资源，四类里最适合目录化；现在每次搜索最多 22 个请求 |
| 详情缓存 | `(site, bookId)` 为 key 写 Cache API，TTL 7 天 | 详情页字段几乎不变，命中即省 20 个请求 |
| 跨站合并 | 合并键 = 归一化书名 + 归一化作者，一本书展示多下载源 | 同一本书在两站各出现一次 |
| 时间预算 | 总预算 8s，超时返回已抓到的部分 + 每源状态 | 现在最坏 60s（详情 10 本 / 并发 3 × 15s 超时） |
| 熔断 | 连续 3 次失败 15 分钟跳过（状态落 D1） | 内存态在 Workers 多 isolate 下不共享 |
| 封面 | 豆瓣图书 `subject_suggest` 补封面/作者/年份 | 实测 613B 可用；知轩 `cover:''` |

## 5. 数据模型

**本轮不新增表。** 原本规划的 `canonical_work` / `scraper_health` 与 `info_hash` 列都先不做，理由如下：

| 规划项 | 处置 | 原因 |
|---|---|---|
| `canonical_work` | 不做 | 归组所需的作品属性（年份/类型/集数）在元数据响应里就有，落库只是省一次请求；在没有本地优先读路径之前，这张表没有消费者 |
| `scraper_health` | 不做 | 熔断状态用 Cache API 存（`utils/breaker.ts`），自带 TTL、跨 isolate 可用，不需要 D1 写放大 |
| `data_record_sources.info_hash` | 不做 | 去重目前发生在单次搜索内（内存 Set）；跨搜索去重需要先有「跨记录重复」的实际数据，否则加列只是空字段 |
| `entity_aliases` 扩 `priority` | 不做 | 现有字段足够，问题在「没被读」，已通过 v0 别名 + 归组候选解决 |

保留 `data_records` 结构不动，改动面越小越好。新增表要等有明确消费者再加，避免无人使用的空表。

**一个必须处理的既有约束**：`data-retention` 会删除 `detail_completed=0 AND source_count=0` 且 180 天未更新的记录。四类入库时至少要写一条 `detail` 来源，否则写入的数据会被静默清掉。

## 6. 时间预算与失败语义（成功率）

成功率最大的隐性杀手是尾部延迟。现状：

| 类别 | 总预算 | 最坏情况 | 结论 |
|---|---|---|---|
| 动漫 | 20s（`ANIME_SEARCH_TIMEOUT_MS`） | 20s + 部分结果 | 有预算，可用 |
| 影视 | **无** | TPB 30s 超时 × 2 次重试 × 2 批 ≈ 90s+ | 必须加 |
| 漫画 | 无 | 10s（两源并发） | 可接受 |
| 小说 | **无** | 详情 4 波 × 15s ≈ 60s | 必须加 |

设计：

1. 每类一个总预算（8s），到期返回**已完成的源**，未完成的标记 `timeout`；
2. 单源超时不得大于总预算的 60%；
3. 失败分三态：`failed`（请求失败）/ `degraded`（200 但可疑空）/ `empty`（真空）。
   **`degraded` 是新增的**：实测 apibay 会用 `HTTP 200 + {"name":"No results returned"}` 表达降级，与真空结果同形，现在直接当空，导致"源挂了"永远不可见。

## 7. 度量闭环

没有标注就没有准确性。设计三层：

1. **决策日志（在线，采样）**：只记"模糊决策"（`margin < 30`）——记录 `rawTitle / chosenId / score / runnerUpId / margin / reason`。这类样本最少、信息量最大。
2. **影子回放（离线）**：抓取缓存已与判定解耦，可把真实原始数据回放给新旧两套 matcher，输出差异集（A 归 B、B 归 A、A 归而 B 不归）。**上线前就能知道改动的方向和幅度**。
3. **标注 → 回归集**：差异集抽样人工判定，正确样本进 `title-grouping.test.ts`。回归集只增不减。

## 8. 迁移路径

原则：**重构判定层与编排，不重写抓取器。** 解析器里的怪癖（TPB 关键词区分大小写、Mikan 要下 `.torrent` 解 infoHash、奇书网 GBK + Cookie 门、MangaDex 必须自定义 UA）都是用线上故障换来的，推倒重来等于重新踩一遍。

| PR | 内容 | 用户可见变化 | 风险 |
|---|---|---|---|
| **PR-1** | 抓取缓存与判定解耦；6 个指标日志；每类 8s 预算；`actionable` 字段 | 无（除超时更快返回） | 低。先拿到基线 |
| **PR-2** | L0 文本层（`parseReleaseTitle` / 打分 / 边际接受）+ 影子模式 | 无（只记录差异） | 低。纯函数 + 单测 |
| **PR-3** | 切换 matcher（灰度开关，按类别开） | 归属变准、死链消失 | 中。有影子数据兜底 |
| **PR-4** | 分类专项：影视 `cat=200`+类型约束+华语片；漫画标题/可读性；动漫 v0+按集 | 明显 | 中。逐类灰度 |
| **PR-5** | 小说目录化 + 漫画元数据入库 | 搜索变快、覆盖变广 | 中高。D1 写放大 |

PR-1 到 PR-3 是纯内部改动，前端零改动即可上线；PR-4 之后才需要前端配合（按集展示、可读性提示）。

## 9. 不做什么

| 不做 | 理由 |
|---|---|
| 新增资源源（1337x / YTS / Torrentio） | 1337x 实测 403、YTS 未测通、Torrentio 首次 200 后连续 internal error。现有源的问题是"用错"，不是"不够" |
| AI 翻译标题做别名 | 不可审计、成本高；元数据源自带别名已够 |
| 全站爬取 | 两站总书量未知，D1 写放大不可控；先做"搜过的词 + 分类页增量" |
| 一次性重写四个 search 服务 | 解析器的怪癖是资产。重写会让成功率先下降再爬回来 |
| 统一四类的线上响应结构 | 内部统一即可，线上契约保持现状，避免同时改前后端 |

## 10. 与旧方案的关键差异（供对照，不必先读旧文）

| 议题 | 旧方案 | 本文 |
|---|---|---|
| 四类抽象 | 共用一个归组引擎 | 拆成资源型 / 目录型两条流水线，只共享 L0/L1 |
| 判定算法 | 最长匹配 + 词边界 | 打分 + 硬约束否决 + 边际接受（宁可漏不可错） |
| 抓取与判定 | 耦合在一个缓存响应里 | 解耦，改算法立即生效，且可影子回放 |
| 时间预算 | 只有动漫有 | 四类统一，`degraded` 三态失败语义 |
| 可操作性 | 未定义 | `actionable` 写进契约，驱动三个指标 |
| 实体身份 | 标题字符串 | `canonical_work` + 全语种别名，ID 优先 |
| 度量 | 最后做 | PR-1 先做，先有基线再改 |
